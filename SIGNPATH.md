# SignPath Foundation / Windows signing

This repository contains the Hyspayre Launcher and Installer source code, with
no private catalog-signing keys, private game builds, service-role tokens or
SMTP passwords. Its Windows binaries are **not Authenticode signed** by default.

## Public repository preparation

- Create a new **public** GitHub repository and upload this source tree, not the
  contents of the private publisher bundle.
- Review `README.md`, `LICENSE`, `SECURITY.md`, `BRAND_ASSETS.md`.
- Confirm that you own or may publish the artwork under an eligible license.
  The code MIT license does **not** automatically license the game art.
- Keep `setup/payload.zip`, `setup/launcher_hash_generated.go` and `dist/` out
  of Git. They are generated by `scripts/build.py` and ignored by `.gitignore`.
- Build/test from source using GitHub Actions (`.github/workflows/build.yml`).

## Build from source

```bash
python scripts/build.py
```

Output files:
- `dist/Hyspayre-Launcher.exe`
- `dist/Hyspayre-Setup.exe`

The installer includes the built Launcher binary and a generated SHA-256 pin.
The visual setup screen uses the bundled `setup/welcome-banner.png`.

## Apply to SignPath Foundation

See the current SignPath Foundation documentation and eligibility terms before
applying. Approval is not guaranteed; an open GitHub repository alone does not
make a project eligible. SignPath may require an established release history,
reproducible/traceable builds, evidence of open-source licensing and reviewable
build provenance.

## Two separate signatures

1. **Authenticode** via SignPath signs Windows PE binaries.
2. **Hyspayre Ed25519 catalog signature** authenticates
   `https://hyspayre.com/launcher/catalog.json` for the launcher updater.

The Ed25519 private key is **not** needed or allowed in public builds.

## Correct signing order for production

1. Build the Launcher EXE from reviewed GitHub sources.
2. Sign the Launcher EXE with SignPath / Authenticode.
3. Rebuild the installer payload from that **already signed Launcher**,
   regenerating the pinned SHA-256. The current `scripts/build.py` builds its
   own unsigned Launcher, so this production stage requires adapting the CI
   pipeline to consume a pre-signed Launcher artifact.
4. Build/sign the Setup EXE using SignPath.
5. Publish signed EXEs on IONOS under `/downloads/`.
6. Update the internal `launcher/catalog.json` with the **final signed**
   Launcher EXE's size and SHA-256, and re-sign the catalog **privately**.

Even a signed EXE may initially trigger Microsoft SmartScreen. Signing improves
publisher identity and provenance but does not promise zero warnings.
